这个站最早只是一组可以直接双击打开的 HTML、CSS 和 JavaScript 文件。它已经有我想要的视觉气质：宋体标题、克制的灰阶、缓慢生长的水墨山峦，以及不会打断阅读的飞鸟。真正的问题不是“还缺哪个框架”，而是怎样让它从一个原型变成可以长期更新的个人站。

我最后没有把页面重写成常见的前端应用。更合适的做法，是保留已经满意的页面壳，只为内容增加一条清楚的生产线。

## 先划清页面与内容的边界

视觉层继续由 `index.html`、`style.css` 和 `site.js` 负责。它们管理布局、路由转场、搜索面板、深浅色切换和 Canvas 动画。这一层变化不频繁，适合保持稳定。

文章、项目、菜单和相册则放进独立的内容目录。文章使用 Markdown，结构化页面使用 JSON。构建脚本读取这些文件，生成浏览器能直接加载的页面数据。这样更新一篇文章时，不需要碰动画代码；调整山体笔触时，也不会误改正文。

> 框架的价值不在于文件更多，而在于让不同变化速度的东西彼此隔离。

## 为什么继续使用 Hash 路由

这个站的路由形如 `#/posts/...`。它不算新潮，却非常适合纯静态发布：服务器只需要返回一个 `index.html`，浏览器负责切换页面。GitHub Pages 不需要额外的重写规则，双击本地文件时也能正常浏览。

对个人站来说，这种约束反而带来确定性。发布目录里没有服务端进程，没有数据库迁移，也不需要为每个文章地址生成一份重复的 HTML 壳。只要静态资源还在，页面就能工作。

## Canvas 只负责气氛

水墨背景是这个站最容易被看见的部分，也是最需要克制的部分。山体由多层随机质量、淡墨底色和细笔触组成，飞鸟的数量、位置与轨迹会在每次进入时变化。但随机并不等于失控：中间阅读区域必须保持干净，运动速度必须慢，动画完成后要退回稳定背景。

我把它看成纸张的一部分，而不是一个独立作品。它可以让页面有呼吸，却不能抢走标题和正文的注意力。深色模式也沿用同一逻辑，只是从宣纸变成碑拓。

## 内容在构建时完成，而不是运行时请求

浏览器不会直接拉取 GitHub 仓库里的 Markdown。构建脚本提前完成解析、标题锚点、阅读时间、搜索索引和 HTML 清理，再把结果写进静态产物。运行时只做展示，因此首屏不依赖 GitHub API，也不会因为接口限流而失去文章。

这条边界还让安全问题更容易理解。Markdown 中允许出现哪些标签和属性，由构建阶段的白名单决定；相册的本地图片路径也会检查是否越过自己的目录。

## 用一次提交完成发布

仓库推送到 `main` 后，GitHub Actions 会安装依赖、生成内容、构建 `dist`，再发布到 GitHub Pages。页面框架与内容可以放在同一仓库，也可以通过 `CONTENT_DIR` 指向另一份内容仓库。

这里没有复杂的部署平台，但已经覆盖我真正需要的流程：本地预览、版本记录、自动构建和公开访问。以后更换自有域名时，变化只发生在发布层，内容模型和页面体验都不必重做。

## 简单不是功能少

这个站仍然有搜索、文章大纲、相册灯箱、响应式布局、深浅色模式和动态背景。简单指的是每个能力都有明确位置，出了问题知道去哪里找。

个人站最珍贵的不是技术栈，而是多年后仍愿意回来写东西。选择一套自己看得懂、改得动、部署得出的结构，比追上每一次框架更新更重要。
