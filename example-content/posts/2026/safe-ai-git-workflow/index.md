AI 编程代理进入一个仓库时，看到的不只是版本库里的代码，还可能看到尚未提交的实验、临时调试和另一项工作留下的修改。对这些状态处理不当，比写错一段新代码更危险：错误代码可以修，覆盖掉的本地工作却未必能够恢复。

安全工作流的第一原则，是把当前工作区当作用户正在使用的现场，而不是一张可以随时还原的空白纸。

## 修改前先确认工作区状态

开始任务前读取 `git status`，可以回答三个基础问题：当前分支是什么、哪些文件已经被修改、有没有未跟踪文件。接下来还要判断这些变化与本次任务是否重叠。

不相关的修改应该保持原样。与任务相关的修改则需要仔细阅读，在现有状态上继续，而不是用仓库版本覆盖。最危险的动作通常不是复杂命令，而是未经确认执行一次看似方便的重置。

## 让差异保持可解释

代理很容易一次生成大量代码，但代码审查仍然要由人理解。每一处变化都应该能追溯到任务目标：修复了哪种输入、增加了哪个状态、消除了什么重复。

如果一个窄任务带来几百行无关格式变化，真正的逻辑修改就会被噪声淹没。保持现有格式、避免顺手重构、只删除本次修改产生的无用代码，能够让差异本身成为一份实现说明。

> 小差异不是保守，而是让错误更容易被发现和撤回。

## 提交是恢复点，不是完成仪式

对有进展性的修改，及时创建 Git 提交可以形成稳定恢复点。提交前仍然要完成构建和必要测试，并确认暂存区只包含本次任务文件。

提交信息应描述结果，例如“为内容仓库生成首页”或“修复移动端文章溢出”，而不是笼统写成“update”。当后续部署失败或新需求改变方向时，清楚的提交能帮助人快速定位应该保留、回退或继续修改的部分。

不过提交不等于上传。推送到远程、创建公开仓库、发布页面都会改变外部状态，必须与用户授权保持一致。代理可以在本地自主整理，但不应该把“写完代码”自动扩大成“对外发布”。

## 用测试保护行为边界

Git 保护的是文件历史，测试保护的是行为历史。修改前知道哪些测试覆盖目标模块，修改后运行同一组测试，才能判断新代码是否破坏旧承诺。

界面项目还需要浏览器验证。DOM 中有元素不代表布局正确，构建成功也不代表资源在子目录部署后仍能加载。截图、控制台日志、图片自然尺寸和横向溢出检查，都是对代码测试的补充。

## 失败时保留证据

命令失败后立即换一条完全不同的路径，容易把真正原因掩盖掉。更有效的做法是先读取错误信息，确认它属于代码、环境、权限还是网络问题，再决定下一步。

如果失败来自沙箱或登录状态，重复改代码不会解决；如果失败来自生成文件语法错误，部署日志也不会替你修复。保留错误输出和当前差异，让每次调整都回应一个具体证据，工作区才会在多轮 AI 协作中保持可信。
