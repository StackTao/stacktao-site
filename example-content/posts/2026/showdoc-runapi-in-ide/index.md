后端接口开发经常被切成几个互不相连的步骤：在 IDE 里读 Controller，到浏览器或文档站确认地址，再去独立请求工具拼参数，最后把结果复制进接口文档。每个工具都能完成自己的部分，但上下文在来回切换时不断丢失。

[ShowDoc RunAPI](https://github.com/StackTao/runapi-plugin) 想解决的就是这段断裂。它是一款 IntelliJ IDEA 插件，从当前 Java 项目的 Spring MVC 源码出发，在 IDE 内完成接口发现、请求调试，并把选中的接口同步到自部署的 ShowDoc RunAPI 项目。

## 扫描的不是字符串，而是 Spring 语义

最直接的实现，是搜索所有带 `@GetMapping` 或 `@PostMapping` 的方法。但真实项目很快会打破这种假设：类和方法可以同时声明路径，一个方法可以有多个 HTTP 方法，接口可能来自继承，自定义框架也会包装一层自己的注解。

插件因此需要先理解“这个注解在 Spring 中代表什么”，再决定它如何进入接口模型。除了标准的 `@RequestMapping` 系列，还可以把项目自定义注解映射到 Spring 的标准语义。配置保存在 IDE 应用级，不需要在每个项目里重复填写。

扫描结果还要合并类级与方法级路径、处理继承方法，并避免同一个 Java 方法因为多路径或多 HTTP 方法而在界面里重复失真。这里的难点不是找到更多接口，而是建立一个接近开发者认知的稳定列表。

## 参数模型决定调试是否可信

一个接口名称和 URL 只能说明入口，真正影响请求能否发送的是参数。插件会识别 `@RequestParam`、`@PathVariable`、`@RequestHeader`、`@CookieValue` 和 `@RequestBody`，并继续展开结构化 DTO。

这些来源必须保持区别。Query 参数不能混进 JSON Body，Path 参数需要准确替换 URL，占位的 Header 与 Cookie 也要留在自己的区域。JavaDoc 中的类说明、方法说明和 `@param` 文本，则可以补上源码类型无法表达的业务含义。

> 自动生成不是替开发者猜测，而是尽可能保留源码已经给出的事实。

## 请求工作台应该覆盖真实接口

如果插件只能发送简单 JSON，它很快就会被真实项目淘汰。ShowDoc RunAPI 的请求工作台支持 JSON、XML、Text、HTML、Form URL Encoded、Multipart Form Data 和 Binary Body。JSON 与 XML 可以格式化、压缩和校验，Multipart 参数能够按字段选择不同文件。

请求基础地址属于项目级配置，因为本地、测试和预发布环境通常不同；ShowDoc 服务地址、用户名和注解映射则属于应用级配置，可以跨项目复用。密码与登录会话交给 IntelliJ Password Safe，而不是写进普通配置文件。

这种配置边界看起来琐碎，却决定了插件是否能在多项目环境里长期使用。范围太小会迫使人重复设置，范围太大又会把不该共享的信息带到另一个项目。

## 上传策略宁可保守

把接口批量上传到文档系统时，覆盖已有页面似乎最省事，但已有页面里可能已经积累了调试用例、响应示例和脚本。一次自动同步如果抹掉这些人工内容，效率工具就会变成风险来源。

当前策略是在目标 RunAPI 项目与文件夹中新建可编辑接口页，不自动覆盖已有页面。它可能产生需要整理的重复项，却不会未经确认破坏已有资料。这是一个有意保守的选择：自动化应该减少重复劳动，而不是扩大一次误操作的影响面。

## IDE 插件也是长期产品

插件以 Kotlin 开发，面向 IntelliJ IDEA 2024.1 及以上版本，使用 JDK 17 和 Gradle Wrapper 构建。PSI 扫描与网络请求放在后台执行，未变化项目的扫描结果会被缓存，避免每次打开工具窗口都重新消耗整棵语法树。

从源码扫描到请求发送，再到 ShowDoc 同步，这条链路包含许多边缘情况。真正值得维护的不是“又一个 API 工具”，而是一段更连续的开发体验：开发者不必离开正在理解的代码，就能验证接口并整理文档。
