AI 编程工具更新很快，围绕它们的经验也很容易变成散落在聊天记录、社交媒体和个人笔记里的碎片。某条命令今天有效，几个月后可能已经改名；一套工作流在个人项目里顺畅，放进团队仓库却可能碰到权限、安全或成本问题。

[Claude Code Guide](https://github.com/StackTao/ClaudeCodeGuide) 是一个面向中文开发者的共建知识库。它收集命令、Prompt、Hooks、MCP、Skills、插件和 GitHub 协作案例，但目标不只是“多收一点技巧”，而是让经验能够被检索、核对、更新和继续讨论。

## 从真实任务组织内容

工具文档常按功能菜单展开，读者却通常带着任务而来：怎样拆解一个改动，怎样让代理检查失败的 CI，怎样安全地接入外部工具，怎样控制上下文和调用成本。

因此知识库把内容分为主指南、命令与案例、Skills 与增强工作流、可复制模板，以及来源索引。数字前缀保持章节顺序，稳定标题尽量避免旧链接失效。结构不追求一次定型，而是让新增内容知道应该落在哪里。

一个经验如果暂时找不到合适章节，也可能说明它还没有被说清楚。先描述适用场景、前提和失败方式，往往比立即给它起一个宏大的分类更有价值。

## 事实与经验要分开写

关于模型能力、命令参数和产品限制的陈述，需要优先引用官方资料。社区技巧可以来自 GitHub、论坛、博客或个人实践，但应该标明来源和适用范围。

这不是为了让每一段文字都像论文，而是防止两种内容混在一起：一种是可以被官方文档验证的事实，另一种是在特定环境中有效的方法。读者只有知道它属于哪一种，才能判断何时照做、何时重新测试。

> 一个可维护的知识库，不只告诉读者“怎么做”，也要说明“为什么现在可以这样做”。

## 失败案例比万能模板更重要

AI 编程最容易传播的是漂亮的成功演示，最难沉淀的是失败过程。上下文为什么失焦，工具为什么没有权限，自动修改为什么破坏了未提交代码，提示词为什么在另一个仓库里失效，这些问题更接近真实工作。

知识库因此欢迎踩坑记录、成本控制、权限安全和上下文管理建议。一个失败案例只要能说清环境、动作、结果和修正方式，就可能比十条抽象原则更有帮助。

模板也应该保留边界。可复制不等于无需理解；涉及账号、令牌、外部消息或删除操作时，模板必须提醒使用者重新确认授权范围。

## 静态站让维护成本可控

整个站点使用 Markdown 保存内容，通过 Node.js 内置模块生成静态数据。开发者通常只需要修改 `content/`，运行构建和检查，再提交 Pull Request。发布由 GitHub Pages 工作流完成，不需要数据库或常驻服务。

这套实现不复杂，却很适合知识库：每次变化都有 Git 历史，章节可以在代码审查中逐行讨论，旧版本也能追溯。静态输出方便搜索和长期托管，未来还可以继续转换为 GitBook、PDF 或其他文档形态。

## 反馈本身也是内容入口

页面底部可以复制修改请求、打开 GitHub Issue 草稿，并跳转到当前章节相关的反馈。即使 GitHub API 被限流，Issue 草稿链接仍然可用。

这让“我发现一处不准确”不必立刻变成一次完整的代码贡献。先留下问题、来源和场景，再由维护者或其他贡献者整理进正文，也是健康的协作路径。

## 让更新速度服从可信度

面对快速变化的工具，知识库不可能保证每一页永远最新。更现实的目标，是让读者看得出内容从哪里来、最近为什么修改、哪些结论仍需要验证。

速度当然重要，但可信度来自可追溯的来源、清楚的边界和愿意修正的结构。把这些基础打好，中文经验才不会随着一次版本更新全部失效，而能逐渐变成真正可复用的共同资产。
